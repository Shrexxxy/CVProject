# Модуль оборудования

Учёт оборудования организации: карточка с валидацией, список с фильтрами, сортировкой и пагинацией
и подбор оборудования для нового ТО. При подборе из выдачи убирается оборудование, которое у того же
исполнителя уже обслуживается в пересекающийся период.

Стек: .NET 9, ASP.NET Core, EF Core 9 + Npgsql (PostgreSQL), FluentValidation, AutoMapper, LinqKit.

## API

| Endpoint | Описание |
|---|---|
| `POST api/equipments/search` | Получить список оборудования по фильтру |
| `GET api/equipments/{id}` | Получить карточку оборудования |
| `POST api/equipments` | Создание карточки оборудования |
| `PUT api/equipments/{id}` | Изменение карточки оборудования |
| `DELETE api/equipments/{id}` | Мягкое удаление карточки оборудования |

## Структура

| Проект | Что внутри |
|---|---|
| `Contracts` | Контракты API: карточка, фильтр, строка списка, пагинация |
| `BL` | Бизнес логика: сущности релейшенов, интерфейсы, сервис, валидаторы, профили маппинга |
| `DAL` | Доступ к данным: контексты EF, репозитории, построитель запросов, миграции, скрипт деплоя |
| `Api` | Точка входа и контроллеры |

Зависимости: `Api -> BL, DAL`, `DAL -> BL`, `BL -> Contracts`. Контроллеры работают только через
интерфейсы из `BL`, а ссылка `Api -> DAL` нужна точке входа, чтобы зарегистрировать реализации в DI.
В исходной системе у каждой сущности был свой модуль, который регистрировал её слой доступа к данным,
и точка входа подключала эти модули.

## Архитектура

Проект собран из фрагмента event-driven системы с большим числом сервисов. Там запись и чтение
разнесены: сервис записи хранит события в отдельных таблицах, а сервис чтения строит из них
материализованное представление, то есть документы и релейшены для поиска. Здесь остались
только таблицы материализованного представления.

### Документ и релейшен

Карточка целиком хранится как версионируемый документ в `jsonb`. Поля для фильтрации и сортировки
продублированы в плоский релейшен. Поиск идёт по релейшену, а документ читается по найденному
`EntityId`, поэтому индексы стоят на релейшене, а у таблицы документов есть только первичный
ключ. Документ и запись релейшена пишутся в одной транзакции.

### Фильтр API и фильтр хранения

Клиент присылает `EquipmentFilterParameters`, репозиторий работает с внутренним
`EquipmentFilterSettings`. В исходной системе контракты публиковались отдельным пакетом для других
сервисов, и такое разделение позволяло менять внутренний фильтр, не ломая их.

### Подбор оборудования для нового ТО

Два периода обслуживания пересекаются, если каждый начинается не позже, чем заканчивается другой.
Обслуживание без даты окончания считается бессрочным.

Занятое оборудование отсекается в том же SQL-запросе через `NOT EXISTS`, так что список занятых
идентификаторов в приложение не загружается. Даты сравниваются с колонками напрямую: если обернуть
колонку в функцию (например, взять `.Date` в LINQ), PostgreSQL не сможет использовать индекс по дате
начала обслуживания.

### Индексы

`DAL/Equipment/EquipmentDbContext.cs`:
- GIN `gin_trgm_ops` по `Name` и `Model` для поиска по подстроке `ILIKE '%...%'`, который обычный
  B-tree не ускоряет;
- частичный `(OrganizationId, UpdateUtcDateTime) WHERE NOT IsDeleted`: список всегда открывается
  в рамках организации, а удалённые записи в индекс не попадают;
- GIN по массиву `EquipmentIds` (`uuid[]`) для проверки, входит ли оборудование в обслуживание;
- частичные `(ContractorOrganizationId, BeginDate)` и `(ContractorEmployeeId, BeginDate)` под подзапрос
  пересечения периодов.

### Запрос списка

Строки проецируются в DTO через `ProjectTo`, поэтому в `SELECT` попадают только нужные колонки,
и читаются без отслеживания. К любой сортировке добавляется `ThenBy(EntityId)`: без уникального
второго ключа записи с одинаковым значением переезжают между страницами. Пользовательский ввод
в `ILIKE` экранируется.

### Даты

Даты хранятся как `date`, потому что значима только дата. Заодно не возникает проблем с `DateTime.Kind`
при записи в `timestamptz`.

### Валидация

Правила карточки перенесены из общей библиотеки валидаторов исходной системы:
- границы дат и их порядок: выпуск, ввод, вывод из эксплуатации;
- дата выпуска указывается с точностью до месяца или года;
- причина вывода обязательна только вместе с датой;
- количество больше 1 допустимо только без серийного и инвентарного номеров («б/н», «нет» и т.п.).

Если в запросе на подбор нет даты начала или исполнителя, валидатор фильтра возвращает 400, иначе
условие подбора было бы молча проигнорировано. `Limit` ограничен сверху.

### Конкурентная запись

`Version` документа используется как токен конкурентности: `UPDATE` уходит с условием
`WHERE "Version" = <ожидаемая>`. Сервис сначала сверяет версию и при расхождении сразу отвечает 409.
Если два запроса пришли одновременно, гонку закрывает сам `UPDATE`, и конфликт тоже возвращается
как 409, а не как исключение.

## Миграции

- `InitialCreate` создаёт схему. `BuildingId` в ней `text`, как в исходной системе.
- `ConvertBuildingIdToUuid` меняет тип на живых данных и написана вручную. Сгенерированный `AlterColumn`
  падает, потому что PostgreSQL не приводит `text` к `uuid` без `USING`. Миграция переносит данные
  через временную колонку, пустые строки превращает в `NULL` через `NULLIF`, а `Down` откатывает
  изменение вместе с данными.

`DAL/Scripts/RefreshEquipmentIndex.sql` взят из исходной системы, где запускался при деплое на каждый
стенд. Когда поле уже было в событиях, а в релейшен его только добавляли, скрипт заполнял его у старых
записей из последней версии события. К схеме этого фрагмента скрипт не применяется.

## Запуск

```bash
docker compose up --build
```

Поднимаются PostgreSQL 16 и API на `http://localhost:8080`. API стартует после готовности базы и в окружении
Development сам применяет миграции. Пароль базы по умолчанию `postgres`, переопределяется переменной
окружения `POSTGRES_PASSWORD`.

Остановить и удалить данные:

```bash
docker compose down -v
```
